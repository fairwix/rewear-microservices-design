# План реализации ReWear

Это последовательность реализации согласованной архитектуры, без расширения пользовательских требований. Авторизация, админка, реальные платежи, email, доставка, кеш и Kubernetes не добавляются.

## Минимальный состав

| Компонент | Что реализовать |
|---|---|
| Catalog | Seed 20–30 вещей, чтение/фильтры, атомарные reserve/complete/release и чтение резерва |
| Cart | Одна корзина на демопокупателя, добавление/удаление, чтение и безопасная очистка купленных позиций |
| Order | Снимок корзины, идемпотентное создание, тестовая оплата, фазы восстановления, outbox и чтение заказа |
| Notification | RabbitMQ consumer, уникальный event_id, сохранение и чтение уведомлений |
| Nginx + статический клиент | Маршрутизация и экраны каталога, карточки, корзины/оформления, заказа, списка уведомлений |
| Инфраструктура | 4 PostgreSQL с отдельными ролями/volumes, RabbitMQ, внутренняя сеть Compose, healthchecks |

Рекомендуемая структура будущего кода: `src/Catalog`, `src/Cart`, `src/Order`, `src/Notification`, `web`, `infra`. Общий DTO-контракт допустим как библиотека, общие бизнес-таблицы — нет. Фоновые задачи Order запускаются в его процессе, а не как пятый микросервис.

## Этапы

1. Создать сервисы, миграции, минимальный Dockerfile каждого; развернуть БД и RabbitMQ в Compose. Проверить изоляцию credentials и хранение данных на volumes.
2. Реализовать Catalog с ограничениями резервов и начальными данными. Сначала проверить конкуренцию двух заказов за один товар и атомарность корзины.
3. Реализовать Cart и пакетное чтение товаров из Catalog; quantity фиксирована как 1 правилом, а не отдельным полем.
4. Реализовать Order и сохранённые фазы. Связать ключ оформления с телом первого запроса; фиксировать состав и результат симулятора до внешних действий.
5. Добавить восстановление PROCESSING: повтор команд после тайм-аута, повтор очистки корзины, сохранённые маркеры RELEASED.
6. Добавить outbox publisher и Notification consumer, publisher confirms, ACK после записи, дедупликацию и dead-letter queue.
7. Собрать минимальный интерфейс. На оформлении сохранить Idempotency-Key до получения результата; при 202 открыть заказ и опрашивать его статус. Для нового заказа создать новый ключ.
8. Подключить gateway, healthchecks и сквозные request_id/order_id/event_id в логах. Зафиксировать версии SDK/образов на этапе разработки.
9. Подготовить README с фактической командой запуска и воспроизводимым сценарием защиты. В текущем репозитории такой команды нет, потому что приложение ещё не реализовано.

## Сценарии будущей приёмки

| Сценарий | Ожидаемый результат |
|---|---|
| Успешная покупка | CONFIRMED, все вещи SOLD у этого order_id, одна запись уведомления, купленные строки удалены из корзины |
| DECLINED | CANCELLED / PAYMENT_DECLINED, все резервы освобождены, корзина сохранена |
| Два покупателя одной вещи | Не более одного подтверждённого заказа; второй получает PRODUCT_UNAVAILABLE |
| Одна недоступная вещь из нескольких | Ни одна из остальных не остаётся частично зарезервированной |
| Повтор POST с тем же ключом и телом | Тот же order_id; нет дополнительных продаж, событий или уведомлений |
| Тот же ключ, другое тело | 409 IDEMPOTENCY_CONFLICT |
| Изменение цены между корзиной и резервом | CANCELLED / PRICE_CHANGED; освобождение резерва и предложение оформить заново |
| Потеря HTTP-ответа reserve/complete | Повтор операции не создаёт новый резерв и не завершает продажу дважды |
| Release приходит до запоздалого reserve | RELEASED запрещает новый захват вещей этим order_id |
| Перезапуск Order после SOLD | PROCESSING восстанавливается до CONFIRMED; проданная вещь не освобождается |
| RabbitMQ остановлен | Итог заказа сохранён; outbox растёт; после старта broker уведомления появляются |
| Повтор одного события | Ровно одно уведомление с этим event_id |
| Сбой Cart после подтверждения | Заказ сохраняет CONFIRMED, очистка повторяется позднее |
| Перезапуск Compose | Заказы и данные сохраняются на volumes; фоновая работа возобновляется |
| Latency | p95 измеряется на профиле из §2.3 отчёта; фактические результаты документируются |

Проверки перечислены как критерии будущей реализации. Они не являются отчётом о выполненных тестах приложения.
