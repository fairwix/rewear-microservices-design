Лабораторная работа №6: Проектирование микросервисной архитектуры
Цель работы
Спроектировать архитектуру микросервисной системы, которую вы будете реализовывать в Лабораторной работе №2. Научиться принимать архитектурные решения, обосновывать выбор паттернов и учитывать trade-offs распределенных систем.

Описание задания
Необходимо спроектировать микросервисную систему на выбранную тему. Система должна состоять из 3-5 микросервисов и быть реализуемой на одной машине через Docker Compose или Minikube.

Темы на выбор:
E-commerce платформа

Примеры сервисов: каталог товаров, корзина, заказы, платежи, доставка
Примеры фич: просмотр товаров, добавление в корзину, оформление заказа, оплата
Онлайн-обучение

Примеры сервисов: курсы, студенты, прогресс обучения, сертификаты, видео
Примеры фич: просмотр курсов, прохождение уроков, выдача сертификатов
Социальная сеть

Примеры сервисов: пользователи, посты, лента новостей, лайки/комментарии, нотификации
Примеры фич: публикация постов, лента друзей, уведомления о новых лайках
Своя тема

Необходимо согласовать с преподавателем
Должна быть достаточно сложной для микросервисной архитектуры
Требования к проекту
Технические constraints:
3-5 микросервисов (не меньше, не больше)
Система должна запускаться на одной машине (Docker Compose или Minikube)
Каждый сервис должен иметь свою базу данных (database per service)
Должна быть как минимум одна асинхронная коммуникация через message broker
Должна быть как минимум одна синхронная коммуникация между сервисами

Sync vs Async коммуникация

Какие операции синхронные (HTTP/gRPC запросы)?
Какие операции асинхронные (через message broker/события)?
Обоснование: почему?
Latency требования

Какие операции должны быть быстрыми (<100ms)?
Какие операции могут выполняться дольше (>1s)?
Обоснование: как это влияет на user experience?
Scalability

Какие сервисы будут нагружены больше всего?
Какие узкие места могут возникнуть при росте нагрузки?
Как планируется масштабировать систему?
Пример для E-commerce:

Consistency модель:
- Strong consistency: 
  - Остатки товара на складе (чтобы не продать больше чем есть)
  - Обработка платежей (критично для денег)
- Eventual consistency:
  - Статистика просмотров товаров (не критично если с задержкой)
  - Статус доставки заказа (обновляется раз в несколько минут)

Sync vs Async:
- Sync (HTTP):
  - Catalog Service → Inventory Service: проверка наличия товара
  - Order Service → Payment Service: обработка оплаты
  - Обоснование: пользователь ждет немедленного ответа
- Async (Events):
  - Order Created → Notification Service: отправка email
  - Order Created → Analytics Service: обновление статистики
  - Обоснование: пользователю не нужно ждать, можно обработать фоном

Latency:
- <100ms: поиск товаров, просмотр каталога (частые операции)
- <500ms: добавление в корзину, оформление заказа
- >1s: генерация отчетов, отправка уведомлений (фоновые задачи)

Scalability:
- Catalog Service - самый нагруженный (просмотры товаров)
- Order Service - средняя нагрузка (только при покупках)
- Payment Service - низкая нагрузка (только успешные заказы)

Пример описания для E-commerce:

Микросервисы:

1. API Gateway
   - Единая точка входа
   - Routing запросов к сервисам
   - Rate limiting

2. Catalog Service
   - Управление каталогом товаров
   - Поиск и фильтрация
   - БД: PostgreSQL

3. Cart Service  
   - Управление корзиной пользователя
   - Добавление/удаление товаров
   - БД: Redis (для быстрого доступа)

4. Order Service
   - Создание заказов
   - Управление статусами заказов
   - БД: PostgreSQL

5. Payment Service
   - Обработка платежей
   - Проверка карт
   - БД: PostgreSQL

6. Notification Service
   - Отправка email/SMS уведомлений
   - БД: PostgreSQL (история уведомлений)

Message Broker: RabbitMQ
Cache: Redis (для Catalog Service - кеширование популярных товаров)

Коммуникация:
- API Gateway → Catalog Service (HTTP GET)
- API Gateway → Cart Service (HTTP POST/GET)
- Order Service → Payment Service (HTTP POST - sync)
- Order Service → [RabbitMQ] → Notification Service (async event)
- Order Service → [RabbitMQ] → Inventory Service (async event)

Пример для E-commerce:

Data Model:

Catalog Service:
- Product (id, name, description, price, category_id)
- Category (id, name)

Cart Service:
- CartItem (user_id, product_id, quantity, added_at)

Order Service:
- Order (id, user_id, total_amount, status, created_at)
- OrderItem (order_id, product_id, quantity, price)

Payment Service:
- Payment (id, order_id, amount, status, payment_method)

Notification Service:
- Notification (id, user_id, type, message, sent_at)

Ownership:
- Product данные принадлежат только Catalog Service
- Order данные принадлежат только Order Service
- Payment данные принадлежат только Payment Service

API между сервисами:

1. GET /catalog/products/{id}
   - Caller: Order Service
   - Response: { id, name, price, available }
   - Зачем: проверить доступность товара при создании заказа

2. GET /catalog/products?ids=1,2,3
   - Caller: Cart Service
   - Response: [{ id, name, price }, ...]
   - Зачем: получить детали товаров в корзине

3. POST /orders
   - Caller: API Gateway
   - Request: { user_id, items: [{ product_id, quantity }] }
   - Response: { order_id, total, status }
   - Зачем: создать новый заказ

4. POST /payments/charge
   - Caller: Order Service
   - Request: { order_id, amount, payment_method }
   - Response: { payment_id, status }
   - Зачем: обработать оплату заказа

5. Event: OrderCreated
   - Publisher: Order Service
   - Consumer: Notification Service
   - Payload: { order_id, user_id, total }
   - Зачем: отправить уведомление пользователю

6. Event: OrderCreated  
   - Publisher: Order Service
   - Consumer: Inventory Service
   - Payload: { order_id, items: [{ product_id, quantity }] }
   - Зачем: уменьшить остатки товара

7. GET /orders/{id}
   - Caller: API Gateway
   - Response: { order_id, status, items, total }
   - Зачем: пользователь смотрит статус заказа

Пример для E-commerce:

1. Декомпозиция:
   - Разделили по bounded contexts: каталог, корзина, заказы, платежи
   - Каждый контекст имеет свою бизнес-логику и может развиваться независимо
   - Альтернатива: один Order Service для заказов+корзины+платежей, 
     но тогда сервис был бы слишком большим

2. Sync vs Async:
   - Sync для Order → Payment: пользователь ждет результата оплаты
   - Async для уведомлений: пользователю не нужно ждать отправки email
   - Если сделать Payment async: пользователь не узнает сразу об ошибке оплаты

3. Возможные проблемы:
   - Payment Service упал → заказы не могут быть оплачены
   - RabbitMQ недоступен → уведомления не отправляются
   - Catalog Service медленный → вся система тормозит
   - Eventual consistency: статистика может отставать от реальности

4. Решения:
   - Circuit breaker для Payment Service: если не отвечает, быстро отдаем ошибку
   - Retry для RabbitMQ: если недоступен, переотправим события позже
   - Кеш для Catalog Service: популярные товары кешируем в Redis
   - Для eventual consistency: показываем пользователю "обрабатывается"
   - Saga pattern для Order: если Payment failed → отменяем Order
